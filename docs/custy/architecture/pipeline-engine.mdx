## Overview

The pipeline package separates workflow definition from execution. Profiles
declare names, the resolver expands nested definitions, the registry maps final
names to classes, builders instantiate those classes, and a pipeline runs every
step against one shared context.

---

<Section title="Pipeline Components">

<Grid columns={2}>

<ArchitectureCard title="Profile Definitions" subtitle="profiles.py" icon={<Icon name="workflow" />}>

`PIPELINE_PROFILES` defines reusable step sequences. `STEP_ORDER` defines the
global priority used only when two or more profiles are composed.

</ArchitectureCard>

<ArchitectureCard title="Command Resolver" subtitle="command_resolver.py" icon={<Icon name="dependency" />}>

Expands nested profiles, detects cycles, rejects unknown names, preserves one
profile's declared order, and normalizes merged profiles.

</ArchitectureCard>

<ArchitectureCard title="Step Registry" subtitle="registry.py and step_registry.py" icon={<Icon name="configuration" />}>

Stores unique name-to-class mappings and creates step instances. Built-in
registration must occur before pipeline construction.

</ArchitectureCard>

<ArchitectureCard title="Builders" subtitle="builder.py" icon={<Icon name="architecture" />}>

Convert resolved dictionaries into step objects and select either the Rich
progress pipeline or the simpler logged pipeline presentation.

</ArchitectureCard>

<ArchitectureCard title="Pipeline" subtitle="pipeline.py" icon={<Icon name="play" />}>

Executes step objects in list order, advances progress after success, stops at
the first exception, and re-raises the original failure.

</ArchitectureCard>

<ArchitectureCard title="Shared Context" subtitle="context.py" icon={<Icon name="git" />}>

Provides the workflow engine, its Git service, optional Commitizen helper, and
mutable fields intended for cross-step runtime state.

</ArchitectureCard>

</Grid>

</Section>

<InfoBox variant="danger" title="Sequential does not mean transactional">

If step seven fails, effects from steps one through six may already exist.
Neither `Pipeline` nor `SimplePipeline` records compensating actions or rolls
back files, commits, tags, pushes, backups, or branch transitions.

</InfoBox>

---

<Section title="Public and Internal Boundaries">

`PIPELINE_PROFILES` contains validation fragments, direct-command profiles,
aggregate maintenance profiles, and six supported Run profiles. The typed
public Run boundary accepts only `commit`, `tag`, `push`, `dev`, `release`, and
`full`. A registry entry makes a step constructible; a profile entry makes it
composable; neither action alone exposes new public CLI syntax.

</Section>

---

<Section title="Presentation Variants">

`PipelineBuilder` creates a Rich progress-enabled `Pipeline` and can hide its
progress task for selected commands. `SimplePipelineBuilder` creates a
`SimplePipeline` with logged step messages. Both use the same registry and
`execute(context)` contract, so presentation does not change the resolved
business sequence.

</Section>
