## Overview

The workflow package turns resolved command arguments into one engine that
owns the services and mutable release state needed by pipeline steps. A step is
usually a thin adapter whose `execute()` method calls one engine method.

<Grid columns={2}>

<ArchitectureCard title="WorkflowConfig" subtitle="workflow_config.py" icon={<Icon name="configuration" />}>

A dataclass containing commit, tag, version, execution, file, staging, force,

</ArchitectureCard>

<ArchitectureCard title="WorkflowEngineBuilder" subtitle="workflow_builder.py" icon={<Icon name="architecture" />}>

Offers fluent setters, maps supported attributes from resolved command models,
validates configuration relationships, and creates the engine.

</ArchitectureCard>

<ArchitectureCard title="WorkflowEngine" subtitle="workflow_engine.py" icon={<Icon name="workflow" />}>

Copies construction input into runtime fields, creates shared services, holds
the active tag and staging state, and exposes one method per workflow phase.

</ArchitectureCard>

<ArchitectureCard title="GitContext" subtitle="pipeline/context.py" icon={<Icon name="git" />}>

Wraps the engine for pipeline execution and exposes its Git service plus
optional cross-step fields. Active steps primarily delegate to engine state.

</ArchitectureCard>

</Grid>

<Section title="Two Orchestration Styles">

The active CLI normally uses pipeline profiles whose individual steps call
phase methods on the engine. `WorkflowEngine.run()` also contains a complete
hard-coded release sequence, but public Run behavior is defined by
`PIPELINE_PROFILES`, the resolver, and registered steps. Contributors should
not assume that changing `run()` changes `custy run release`.

</Section>

---

<InfoBox variant="warning" title="Builder transport is explicit">

`from_cli_args()` maps known attribute names one by one. Adding a CLI option or
AppContext field does not automatically make it available to the engine. The
command resolver, argument model, WorkflowConfig, builder, engine, and tests
must agree on the name and semantics.

</InfoBox>

---

<Section title="State and Failure Boundaries">

- The engine holds mutable tag, tag-message, workflow-case, and staged-file
  state across phase calls.
- `GitContext` references the same engine and Git service; active steps mostly
  use engine-owned state rather than copying values into context fields.
- Engine methods convert many service failures into actionable
  `ValidationError` instances, but the pipeline re-raises and stops.
- The engine does not record a transaction log or compensation plan, so a
  later failure does not reverse earlier effects.
- Dry-run checks exist both in workflow methods and lower-level runner-backed
  services, but reads, validation, resolution, and prompts can still occur.

</Section>

---

<InfoBox variant="danger" title="Finalization is experimental">

`execute_post_workflow()` can run branch transitions after commit, tag, and
push when the required workflow context exists. The Full profile includes this
finalization step; treat its checkout, rebase, merge, push, and cleanup behavior
as experimental and inspect repository state before retrying a failure.

</InfoBox>
