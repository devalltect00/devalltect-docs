## Overview

These answers clarify the boundaries of standalone changelog generation and
the project settings that affect its result.

<InfoBox
    variant="note"
    title="Use the direct command"
>

The supported standalone form is `custy changelog generate`. The internal
changelog profile is not a public `custy run` argument.

</InfoBox>

---

<Section
    title="Does Generation Change Git History?"
>

No. The standalone command writes the changelog file but does not itself create
a commit or tag. A larger public profile may perform those later stages.

</Section>

---

<Section
    title="Can I Run `custy run changelog`?"
>

No. `changelog` is currently an internal profile name, not an accepted public
`custy run` argument. Use `custy changelog generate`.

</Section>

---

<Section
    title="Must Every Commit Use Conventional Commits?"
>

Structured messages give the parser the most reliable type, scope, and breaking
change information. Unstructured messages may be classified differently or
excluded depending on configuration.

</Section>

---

<Section
    title="Will `--force` Ignore All Configuration?"
>

No. It changes the force-generation decision; collection, parsing, grouping,
release, link, and rendering settings still apply.

</Section>

---

## How Do I Generate a Changelog from Git History Only?

<Section>

In your project's `.config/custy/config.toml`, set `enabled = false` in the
existing pending-commit section:

<Terminal title="Exclude the pending message" language="toml">

{`[tool.custy.changelog.pending_commit]
enabled = false`}

</Terminal>

Then run `custy changelog generate` as usual. You do not need to delete or empty
`commit-message.txt`; it remains available for commit operations. Messages
already committed to Git can still appear through history, subject to your
changelog filters.

See [Pending Commit configuration](../../../configuration/changelog/pending-commit#generate-from-git-history-only)
for the setting comparison and regeneration example.

</Section>

---

<Section
    title="Can I Keep Manual Content in `CHANGELOG.md`?"
>

That depends on the selected generation and integration behavior. Test the
configuration on a reviewed branch and inspect the full diff before adopting a
workflow that mixes generated and manual content.

</Section>

---

<Section
    title="Where Should I Configure the Generator?"
>

Use `.config/custy/config.toml`. CLI flags are best for one-time overrides;
project configuration is better for repeatable team behavior.

</Section>
