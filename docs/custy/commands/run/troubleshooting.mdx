## Overview

Pipeline recovery begins by identifying the last completed stage. Do not assume
that a failed profile left every file, reference, and remote unchanged.

<InfoBox
    variant="warning"
    title="Inspect partial state"
>

Generated files, backups, commits, tags, or successful remote operations can
remain after a later stage fails.

</InfoBox>

---

## The Profile Name Is Rejected

<Section compact>

Use only `commit`, `tag`, `push`, `dev`, `release`, or `full`. Help text that
lists internal names is ahead of the typed public argument.

</Section>

---

## A Combined Sequence Runs in a Different Order

<Section compact>

The resolver globally orders deduplicated steps. This is expected and prevents
the command-line order from placing push before preparation or commit.

</Section>

---

## Validation Stops the Pipeline

<Section compact>

Fix the first reported condition. Later stages are intentionally not executed
after required validation fails.

</Section>

---

## The Pipeline Stopped After Changing Files

<Section compact>

<Terminal>

{`git status -sb
git diff
git log -1 --decorate --stat
git tag --points-at HEAD`}

</Terminal>

Inspect generated artifacts and backups. Determine the last completed stage
before retrying; do not blindly rerun a partially completed release.

</Section>

---

## A Run Option Had No Effect

<Section compact>

Review [Run options](./options) and the effective project configuration.
Explicit CLI remote selection has the highest priority; otherwise Custy applies
the configured main, backup, synchronization, and `push_to` behavior.

</Section>

---

## The Editor Could Not Open in Docker

<Section compact>

Use an interactive container so the bundled Micro, Nano, Vim, or Vi editor can
access the terminal. Micro is the default container candidate. The project
mount remains live while the editor is open.

<Terminal title="Interactive Docker release" language="powershell">

{`docker run --rm -it -v "\${PWD}:/workspace" -w /workspace custy-prod:latest run release`}

</Terminal>

Custy checks `VISUAL` and `EDITOR` first when enabled, then follows
`tool.custy.editor.candidates.container`. An override must name an editor
installed inside the container, not an editor available only on the host. See
[Editor configuration](../../configuration/editor) for identifiers and
precedence. If a run already failed at `EditFilesStep`, inspect the generated
commit and tag message files before retrying because `GenerateArtifactsStep`
completed first.

An unavailable editor is skipped. A process that starts and then returns an
error produces `EDITOR_PROCESS_FAILED`; Custy does not open another editor after
the user may already have edited the message.

<InfoBox variant="warning" title="Non-interactive execution">

Without `-it`, terminal editors are skipped and Custy reports an actionable
`EDITOR_LAUNCH_FAILED` error. Dry-run simulates the editor step and does not
launch an editor.

</InfoBox>

</Section>

---

## Progress Overlaps Terminal Editor Content

<Section compact>

Current Custy releases suspend the live pipeline progress display while Micro,
Nano, Vim, or Vi owns the terminal. The display resumes after the editor closes,
so an `EditFilesStep` row should not cover or repeat inside the message buffer.
This presentation handoff does not modify the file being edited.

If progress rows still appear inside the editor, first save or discard the
message normally and exit the editor. Then verify that the local executable or
container image matches the Custy build you intended to test:

<Terminal title="Check the running Custy version" language="powershell">

{`custy --version
docker run --rm custy-prod:latest --version`}

</Terminal>

For a locally built image, rebuild the production target after updating the
source, then retry with `-it`. An old executable or cached image can retain the
earlier progress behavior even when the project files already contain the fix.

<InfoBox variant="info" title="Useful details for a bug report">

Include the Custy version, full Docker or local command, selected editor, host
terminal, and whether the overlap disappears after rebuilding the image.

</InfoBox>

</Section>
