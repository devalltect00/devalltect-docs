## Overview

Version Update follows a structured workflow that validates the project,
determines the next version, and synchronizes version information across the
appropriate project files.

The same workflow is used whether the command is executed directly or as part
of a larger workflow through `custy run`.

<Section
    title="Workflow Stages"
>

<WorkflowStep
    title="1. Validate Project"
>

Custy verifies the Git repository and configuration needed for Version Update.
An explicitly configured version target must exist. Automatic mode accepts a
project without supported metadata and treats it as Git-tag-only instead of
failing during startup.

</WorkflowStep>

<WorkflowStep
    title="2. Generate the Next Version"
>

Custy determines the version to apply.

The version may come from:

- an explicit command-line version,
- the configured versioning strategy,
- automatic project strategy detection.

Once determined, this version becomes the source for every subsequent update.

</WorkflowStep>

<WorkflowStep
    title="3. Prepare the Tag Message"
>

Custy resolves the tag message by using:

- a command-line value,
- an existing tag message template,
- or a newly generated default template.

Although Version Update does not create Git tags, preparing the tag message
keeps the project ready for later tagging workflows.

</WorkflowStep>

<WorkflowStep
    title="4. Detect the Project Type"
>

Before updating project files, Custy detects root-level Python, Node.js, and
PHP markers. A repository can belong to more than one ecosystem. If no marker
exists, Custy uses a generic layout and safely falls back to the project root.

This ensures that only the appropriate files are modified.

</WorkflowStep>

<WorkflowStep
    title="5. Synchronize Version Files"
>

Custy applies the generated version to every supported version file.

Depending on the detected project type, this may include:

- Python `__version__.py` or static `pyproject.toml` metadata,
- Node.js `package.json` and a supported root lockfile,
- both sets for mixed projects,
- no metadata write for a generic or tag-only project.

Metadata receives the normalized version value without a leading `v`. Dry-run
mode reports the planned targets without writing them.

</WorkflowStep>

</Section>

---

<InfoBox
    variant="tip"
    title="Generation Before Synchronization"
>

Custy always determines the version number before updating project files.

Separating version generation from file synchronization allows different
versioning strategies to share the same synchronization workflow.

</InfoBox>

---

<Section
    title="Workflow Execution"
>

Larger public profiles reuse the necessary version stages internally. The
internal `apply_version` profile name is not accepted by the current public Run
argument, so standalone updates use `custy version update`.

</Section>
