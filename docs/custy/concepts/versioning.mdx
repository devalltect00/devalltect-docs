## Overview

Custy's version lifecycle has separate responsibilities. A strategy determines
the next release value, preparation makes that value available to later steps,
application synchronizes project files, and a tag operation records the
release in Git.

<InfoBox
    variant="info"
    title="A version value is not a Git tag"
>

Resolving or applying a version does not by itself create a Git tag. Tagging is
a later, explicit command or pipeline step with its own validation, message,
and side effects.

</InfoBox>

<Section
    title="Cross-Ecosystem Synchronization"
>

The release value and the representation written to a project file do not
always have identical syntax. Custy's version bridge supports basic conversion
between SemVer and PEP 440 so one release context can update projects that use
different ecosystem conventions.

<InfoBox
    variant="warning"
    title="Review converted values"
>

Version-format conversion is intentionally limited to supported forms. Preview
the resolved version and inspect every updated project file when prerelease,
development, post-release, or build metadata is involved.

</InfoBox>

</Section>

<Section
    title="Choose the Right Layer"
>

- Use the Version command when you need version-specific generation or
  synchronization behavior.
- Use the Tag command when you already understand the version and need a local
  Git reference.
- Use the Release profile when version preparation, changelog generation,
  commit, tag, and push should occur as one ordered pipeline.
- Use dry-run mode and inspect affected project files before applying a release
  value normally.

</Section>
