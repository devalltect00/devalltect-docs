## Overview

This quick start prepares a repository without immediately creating commits,
tags, or remote updates. Initialization writes project resources, validation
checks readiness, and the final pipeline command uses global dry-run mode.

<InfoBox
    variant="tip"
    title="Run commands from the project root"
>

Custy resolves `.config/custy/`, version files, templates, Git state, and
remotes relative to the current project. Confirm the working directory before
you begin.

</InfoBox>

<Section
    title="Initialize Custy"
>

Run the default initialization mode, then inspect everything it added or
skipped.

<Terminal title="Initialize and inspect" language="bash">

{`custy init
git status --short`}

</Terminal>

The default `all` mode can create configuration, templates, example resources,
and a version file. Existing files are preserved unless force behavior is
selected. If an examples directory already exists, Custy still adds missing
nested packaged examples without replacing existing example files.

<Terminal title="Review repository links and remotes" language="bash">

{`git remote -v
# Edit .config/custy/config.toml, then validate it.
custy validate`}

</Terminal>

<InfoBox variant="note" title="A repository URL is not a remote name">

`tool.custy.changelog.links.repository` is an optional HTTP(S) browser URL for
links in `CHANGELOG.md`. `default_remote`, `main_remotes`, and
`backup_remotes` contain Git remote names such as `origin` or `mirror`.

</InfoBox>

<InfoBox
    variant="warning"
    title="Do not use force during initial review"
>

`custy init --force` can overwrite generated resources. Start with `custy init`
and inspect skipped files before choosing any overwrite behavior.

</InfoBox>

</Section>

<Section
    title="Validate the Repository"
>

Run validation after reviewing the generated project workspace.

<Terminal title="Run the readiness checks" language="bash">

{`custy validate`}

</Terminal>

Validation checks repository state and workflow prerequisites such as required
files, configuration, version resources, staged changes, and remotes. Resolve
reported failures before moving to a pipeline.

</Section>

---

<Section
    title="Preview a Pipeline"
>

Use the global `--dry-run` option before the command name. The following preview
resolves the public Dev profile without intentionally applying its normal file,
commit, and push effects.

<Terminal title="Preview daily development" language="bash">

{`custy --dry-run run dev`}

</Terminal>

<InfoBox
    variant="warning"
    title="Preview is the quick-start finish line"
>

Do not remove `--dry-run` merely because the command completed. First review the
resolved stages, message files, version behavior, Git changes, and push
destination described in the Dev profile documentation.

</InfoBox>

</Section>
