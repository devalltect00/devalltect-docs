## Process Status Reference

<KeyValueTable
    title="Current Status Behavior"
    items={[
        {key: "0 - successful completion", value: "A command or pipeline reached its normal completion boundary without an uncaught failure."},

        {key: "Subprocess status", value: "Git, Commitizen, or editor commands have their own return codes. Custy may wrap, normalize, log, or re-raise those failures rather than expose the same numeric value."},
    ]}
/>

<InfoBox variant="warning" title="Root help and version currently exit with 1">

The current root callbacks explicitly use status `1` after displaying
`custy --help`, displaying `custy --version`, or showing root help because no
command was selected. Do not assume these two informational root options return
zero in automation until the implementation changes.

</InfoBox>

<Section title="Structured Validation Labels">

The active workflow and commit validator attach labels such as:

- Repository and remotes: `NOT_GIT_REPO`, `REMOTE_NOT_FOUND`,
  `MAIN_REMOTE_MISSING`.
- Files and editor: `VERSION_FILE_NOT_FOUND`, `COMMIT_MSG_PATH_MISSING`,
  `COMMIT_MSG_FILE_NOT_FOUND`, `TAG_MSG_PATH_MISSING`,
  `TAG_MSG_FILE_NOT_FOUND`, `EDITOR_LAUNCH_FAILED`.
- Commit content: `EMPTY_COMMIT_MSG`, `INVALID_COMMIT_FORMAT`,
  `INVALID_COMMIT_TYPE`, `COMMIT_MESSAGE_MISSING`,
  `COMMITIZEN_CONVENTION_FAILED`, `COMMITIZEN_FAILED`.
- Staging: `EMPTY_STAGING_ABORTED`, `NO_STAGED_FILES`,
  `NO_STAGED_CHANGES`, `INVALID_STAGE_MODE`, `AUTO_STAGE_FAILED`,
  `STAGING_FAILED`.
- Version and tag: `INVALID_VERSION_INPUT`, `TAG_MISSING`,
  `TAG_CREATION_FAILED`.
- Publication and finalization: `COMMIT_FAILED`, `PUSH_FAILED`,
  `PUSH_TAG_FAILED`, `POST_WORKFLOW_FAILED`.

<InfoBox variant="note" title="Labels are diagnostic, not stable numeric codes">

These strings help people and logs identify the failing condition. Custy does
not currently publish a centralized, versioned error-code registry, and one
active commit-validator label even contains spaces. Automation should use the
documented process status and observable result, not parse these labels as a
permanent API.

</InfoBox>

</Section>

---

<Section title="Pipeline Failure Boundary">

Pipelines are sequential and non-transactional. When a step fails:

1. The active pipeline reports the step name.
2. Execution stops before later steps run.
3. The exception is re-raised.
4. Earlier file, Git, backup, commit, tag, or remote effects are not
   automatically reversed.

Inspect `git status`, recent commits, tags, remotes, generated files, backups,
and `logs/custy.log` before retrying.

</Section>

<Section title="Automation Pattern">

<Terminal title="PowerShell" language="powershell">

{`custy --no-banner validate
if ($LASTEXITCODE -ne 0) {
    throw "Custy validation failed with exit code $LASTEXITCODE"
}`}

</Terminal>

Use `--no-banner` for compact output and a UTF-8-capable capture stream. Do not
use root `--help` or `--version` as zero-status health checks with the current
implementation.

</Section>
