## First Principle

A failed Custy pipeline is not necessarily an untouched pipeline. Earlier steps
may have generated or edited files, pruned backups, staged changes, created a
commit or tag, or updated one or more remotes.

<InfoBox variant="danger" title="Do not begin recovery by rerunning everything">

First identify the failed step and the last durable effect. A full retry can
collide with an existing commit or tag, duplicate work, or publish to a remote
that already succeeded.

</InfoBox>

<Section title="Evidence Checklist">

<Terminal title="Inspect local state" language="bash">

{`git status --short --branch
git diff
git diff --staged
git log -3 --decorate --stat
git tag --points-at HEAD
git branch --all
git remote -v`}

</Terminal>

<Section title="Improve Diagnostic Output">

Global options belong before the command group.

<Terminal title="Diagnostic invocations" language="bash">

{`custy --debug run release
custy --log-level DEBUG run dev
custy --debug cleanup brancheses --prefix feature/`}

</Terminal>

Use debug output to understand resolution and execution, but do not include
secrets, tokens, or sensitive remote credentials when sharing logs.

</Section>

---

<InfoBox variant="warning" title="Dry-run after correction does not prove rollback">

A corrected dry-run previews the next execution from the state that exists now.
It does not reverse or hide effects left by the failed run. Reinspect state
before and after the preview.

</InfoBox>

---

<Section title="Escalate When State Is Unclear">

Stop and ask a teammate or repository administrator before deleting commits or
tags, force-pushing, changing shared branches, restoring remote branches, or
rewriting published release history. Preserve logs and current state while the
recovery decision is reviewed.

</Section>
