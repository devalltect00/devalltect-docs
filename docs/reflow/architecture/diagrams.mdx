# Architecture Diagrams

## Overview

Reflow uses diagrams to document architecture, workflows, and command lifecycles.

These diagrams complement the written documentation and provide a visual representation of how the system operates.

The diagrams are maintained in:

```text id="l0y7sq"
docs/diagrams/
```

and are written using:

```text id="z3m4vt"
Mermaid
```

---

# Why Diagrams?

Documentation and code serve different purposes.

Code explains:

```text id="j4x8rp"
How something is implemented
```

Documentation explains:

```text id="v7q3tn"
Why something exists
```

Diagrams explain:

```text id="m2v9pk"
How components interact
```

---

# Diagram Categories

Reflow diagrams are grouped into four categories.


# Diagram Standards

All diagrams should:

```text id="d8v4pk"
Be simple
Be readable
Use consistent naming
Reflect actual behavior
```

---

# Naming Convention

Preferred:

```text id="h4q7rp"
init-workflow.mmd
convert-workflow.mmd
replay-workflow.mmd
dockerize-workflow.mmd
```

Avoid:

```text id="w9v2tn"
diagram1.mmd
test.mmd
newflow.mmd
```

---

# Mermaid Standard

Preferred:

```text id="m3q8pk"
flowchart TD
```

for most workflow diagrams.

Benefits:

```text id="t7v4rp"
Simple
Portable
Easy to maintain
```

---

# When To Create A Diagram

Create a new diagram when:

```text id="k5q2tn"
A workflow becomes difficult to explain
A new architecture layer is introduced
A major feature is added
```

Examples:

```text id="u8v3pk"
New command
New service
New provider
```

---

# Updating Diagrams

Whenever behavior changes:

Update:

```text id="g2q9rp"
Documentation
Diagrams
Examples
```

together.

Avoid situations where:

```text id="p6v4tn"
Code
≠
Documentation
≠
Diagrams
```
