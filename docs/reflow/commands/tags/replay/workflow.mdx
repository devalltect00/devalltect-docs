# Replay Existing Tags Workflow

## Overview

This document explains how the replay workflow executes internally.

The replay command is implemented through the Reflow orchestration layer and operates on existing Git tags.

The goal is to re-process tags without creating new versions.

---

# High-Level Workflow

```text
Git Repository
        │
        ▼
Load Tags
        │
        ▼
Filter Tags
        │
        ▼
Check Release State
        │
        ▼
Replay Tag
        │
        ▼
Continue
```

---

# Detailed Workflow

## Step 1 — Validate Repository

The command first verifies that the current directory is a valid Git repository.

Workflow:

1. Execute Git validation.
2. Confirm repository state.
3. Stop if repository is invalid.

Failure result:

```text
Not a Git repository.
```

---

## Step 2 — Load Tags

The command loads all tags from the repository.

Workflow:

1. Query Git tags.
2. Build tag list.
3. Sort tags according to Git output.

Example:

```text
v1.0.0
v1.1.0
v1.2.0
```

---

## Step 3 — Filter Tags

Optional filtering may be applied.

Examples:

### Stable Releases Only

```bash
reflow tags replay --only-stable
```

Result:

```text
v1.0.0
v2.0.0
```

Skipped:

```text
v2.0.0rc1
v2.0.0-beta1
v2.0.0-alpha1
```

### Limit Processing

```bash
reflow tags replay --limit 10
```

Only the first ten selected tags are processed.

---

## Step 4 — Process Tag

Each tag is processed independently.

Workflow:

1. Select tag.
2. Check release state.
3. Determine required action.
4. Replay tag.
5. Continue.

Example:

```text
Processing:

v1.0.0
v1.1.0
v1.2.0
```

---

## Step 5 — Release Validation

The orchestration layer checks whether a release already exists.

Possible states:

### Release Exists

```text
Tag exists
Release exists
```

Action:

```text
Replay tag
```

### Release Missing

```text
Tag exists
Release missing
```

Action:

```text
Push tag
```

This allows downstream release automation to recreate missing releases.

---

## Step 6 — Replay Tag

Replay behavior depends on release state.

Typical workflow:

```text
Delete remote tag
        │
        ▼
Push tag again
```

The tag version itself does not change.

Only the tag event is replayed.

---

## Step 7 — Continue Processing

The command continues until all selected tags have been processed.

Failures are isolated per tag.

Example:

```text
v1.0.0   SUCCESS
v1.1.0   FAILED
v1.2.0   SUCCESS
```

The workflow continues whenever possible.

---

# Failure Handling

Replay is designed to continue processing remaining tags.

Example:

```text
Tag A   SUCCESS
Tag B   FAILED
Tag C   SUCCESS
```

One failure does not stop the entire operation.

---

# Before and After

## Before Replay

```text
Tag exists
Release missing
Workflow never triggered
```

## After Replay

```text
Tag replayed
Workflow triggered
Release recreated
```

# Summary

Replay is a recovery and automation command.

It does not create new versions.

Instead, it replays existing tag events so release automation can execute again.
