# Developer Guide

## Overview

This guide explains how Reflow is developed and maintained.

It serves as the primary reference for contributors and maintainers.

Topics include:

- Architecture principles
- Coding standards
- Testing philosophy
- Refactoring guidelines
- Documentation standards

---

# Development Philosophy

Reflow follows several core principles:

```text id="p5m8xa"
Simple
Testable
Maintainable
Extensible
```

When introducing new features, prefer:

```text id="v3n7tk"
Small changes
Clear responsibilities
Incremental refactoring
```

over large rewrites.

---

# Architecture Principles

Reflow follows a layered architecture.

```text id="f4k9yb"
CLI
 ↓
Resolver
 ↓
Core
 ↓
Service
 ↓
Executor
 ↓
External Tool
```

Each layer has a specific responsibility.

---

# CLI Layer

Location:

```text id="d2r6vp"
app/cli/
```

Responsibilities:

```text id="u8x4tm"
Commands
Options
Help messages
Presentation
```

The CLI should not contain business logic.

Preferred:

```text id="m5t9rq"
CLI
 ↓
Resolver
 ↓
Core
```

Avoid:

```text id="k7v3pd"
CLI
 ↓
Business Logic
```

---

# Resolver Layer

Location:

```text id="r1m8yk"
app/cli/**/resolver.py
```

Responsibilities:

```text id="g4t7vn"
Configuration loading
Option resolution
Argument transformation
Validation
```

Resolvers prepare data for the core layer.

---

# Core Layer

Location:

```text id="x9v4tk"
app/core/
```

Responsibilities:

```text id="m8p2dq"
Business rules
Workflows
Application behavior
```

The core layer should not depend on Typer or Rich.

---

# Service Layer

Responsibilities:

```text id="a6r3mv"
Git operations
Docker operations
Release operations
```

Services expose high-level actions.

Example:

```text id="t2n9yk"
GitService
DockerService
```

---

# Executor Layer

Responsibilities:

```text id="f7x5pk"
Command execution
Process handling
External tool invocation
```

Executors are the boundary between Reflow and external tools.

---

# Dependency Direction

Preferred:

```text id="z4m8vt"
CLI
 ↓
Core
 ↓
Service
 ↓
Executor
```

Avoid:

```text id="n3q7pk"
Executor
 ↓
CLI
```

Dependencies should flow downward.

---

# Coding Standards

## Type Hints

Always use type annotations.

Preferred:

```python
def convert_tag(tag: str) -> str:
    ...
```

Avoid:

```python
def convert_tag(tag):
    ...
```

---

## Docstrings

Public functions should include docstrings.

Preferred structure:

```python
"""
Convert a tag to SemVer format.

Workflow:
1. Read source tag
2. Convert version
3. Create new tag
4. Return result
"""
```

Workflow sections are encouraged when behavior is non-trivial.

---

## Naming

Use descriptive names.

Preferred:

```python
converted_tag
resolved_config
docker_service
```

Avoid:

```python
tmp
x
data2
```

---

# Refactoring Guidelines

Before refactoring:

```text id="h6v2rp"
Understand behavior
Write tests
Preserve functionality
```

Refactoring should not change behavior unless explicitly intended.

---

# Preferred Refactoring Strategy

```text id="g8m4tk"
Extract Function
      ↓
Extract Class
      ↓
Move Responsibility
      ↓
Simplify
```

Avoid large rewrites when smaller steps are possible.

---

# Testing Philosophy

Reflow emphasizes:

```text id="n5r8vy"
Behavior
Coverage
Maintainability
```

Tests should verify behavior rather than implementation details.

---

## Preferred Test Structure

```python
def test_convert_tag() -> None:
    ...
```

Use clear names that describe behavior.

---

## Coverage Goals

Target:

```text id="d3v7tk"
90%+
```

Core workflows should ideally reach:

```text id="m9x4rp"
100%
```

when practical.

---

# Documentation Standards

Documentation should answer:

```text id="v4q8tn"
What?
Why?
How?
```

before discussing implementation details.

---

# Documentation Structure

Preferred:

```text id="u7m3pk"
Overview
Workflow
Examples
FAQ
```

This structure is used throughout Reflow.

Examples:

```text id="r2x6tv"
docs/init/
docs/tags/
docs/dockerize/
```

---

# UI Standards

Location:

```text id="y8p4rk"
app/ui/
```

Preferred:

```text id="k5m7vt"
Panels
Tables
Progress bars
```

Avoid:

```text id="q3r9xp"
Raw print statements
Repeated formatting
```

Use shared UI helpers whenever possible.

---

# Configuration Standards

Configuration should live in:

```text id="p6t4vn"
config.toml
```

Avoid scattering configuration across multiple files.

---

# Error Handling

Prefer:

```text id="m1x8tk"
Specific exceptions
```

Example:

```python
except ReflowError:
    ...
```

Avoid:

```python
except Exception:
    ...
```

unless absolutely necessary.

---

# Adding New Commands

Recommended workflow:

```text id="z7q4rp"
Command
    ↓
Resolver
    ↓
Models
    ↓
Core
    ↓
Tests
```

Avoid placing business logic directly in command files.
